# Вопросы разработки и инструкция разметки

`development_questions.jsonl`: 36 открытых случаев, из них 24 вопроса с известным подтверждением и 12 сценариев поведения. Все составлены моделью в ходе HW2 после чтения документов/постановки. Это не реальные обращения, не независимый golden set и не закрытый test. Независимой проверки человеком ещё нет. Точечные значения в reference answer описывают снимок кампании 2026, не обещания для будущей кампании.

## Схема

| Поле | Значение |
|---|---|
| `question_id` | Уникальный ID случая |
| `group_id` | Группа одного информационного намерения; новые переформулировки наследуют её |
| `split` | Сейчас только `development` |
| `origin` | `model_authored_source_grounded` или `model_authored_policy_case` |
| `question` | Собственная формулировка вопроса |
| `expected_action` | Ответ по снимку, уточнение, оператор или отказ |
| `reference_answer` | Краткая смысловая опора; не автоматически показанный ответ бота |
| `relevant_url`, `raw_sha256` | Источник и версия подтверждения |
| `evidence_start/end` | `[start,end)` в очищенном тексте HTML; для policy-case пусто |
| `evidence_sha256` | Хеш UTF-8 подтверждающего span |
| `annotation_status` | `single_pass_no_independent_review` |

Один отмеченный источник не означает, что остальные нерелевантны. При проверке top-k нужно добавлять альтернативные подтверждения, а не считать любой другой URL ошибкой. Для policy-case отсутствие evidence не является результатом полного автоматического поиска по всем возможным источникам: это сценарий относительно границ текущего продукта.

## Правила будущей независимой разметки

1. Сначала сформулировать вопрос без чтения ответного текста: реальные обезличенные обращения либо независимые вопросы студентов. Указать происхождение и согласованное использование данных. Синтетику помечать отдельно.
2. Зафиксировать год, уровень образования и категорию поступающего. При недостающем критичном условии ожидаем уточнение.
3. Разметить answerability по замороженному корпусу. Найти все известные поддерживающие секции, указать URL, версию, offsets; для отсутствия ответа записать, что проверено.
4. Эталонный ответ не должен делать более сильное утверждение, чем источник. Например, информация об общежитиях не гарантирует место каждому. Минимальный балл не является проходным.
5. Разделять «нет ответа», «есть конфликт», «непонятен вопрос», «нужен персональный доступ» и «недопустимое действие».
6. Для ответа модели оценивать отдельно: правильность, полноту, критическую ошибку, подтверждение каждого существенного утверждения, корректность и полноту цитирования. Спорные случаи передать второму аннотатору.
7. На 20% выборки выполнить две независимые разметки и согласование. Публиковать число расхождений и причины, а не только общий балл.
8. До экспериментов разбить группы: development / calibration / closed test. Переформулировки и близкие дубликаты не разделять. Текущие 36 случаев остаются development навсегда; просмотренный test нельзя переименовать в новый независимый test.

Для тех же групп источников синтетика может переоценивать lexical retrieval и создавать зависимость наблюдений. Будущие метрики считать раздельно по происхождению и критическим темам. До появления реальных запросов качество на них считается неизвестным.
